# ENH-011 — Strict label check, so that every new module ships translated labels for its config fields
- Reported: 2026-11-13 (from ISS-003, after the user asked whether the fix applies to all future modules)
- Type: enhancement (the user asked "will this fix be applied to all future modules development?" and then clarified "all new modules will show localized labels rather than the internal id string"; the spec check showed that MOD-46 is a MUST but is checked only as a warning, so a module can ship without labels and still be compliant; the user can change this)
- Priority: P2 (proposed by Claude: not stated by the user; nice to have, with no workaround needed for the modules that exist, since their catalogs are complete; the user can change it)
- Area: tooling (`mm3 module check`, `src/mm3/core/modcheck/`), the `mm3 new-module` scaffold (`src/mm3/cli/new_module_cmd.py`), module-index CI (repository `mm3-project/module-index`), specs (Core spec and Module Contract)
- Spec versions at report: Core spec 0.40, Module Contract 1.0 rev 15
- Description: "I meant all new modules will show localized labels rather than the internal id string" (as reported, after ISS-003 was coded). Claude's answer: only if each module ships `title` and `description` for its fields and the matching catalog entries, because the form falls back silently to the field name, so a new module that forgets them looks like the problem ISS-003 reported. Claude proposed a strict mode of `mm3 module check`, used in the module template and in the module-index CI; the user said "Yes" and chose, from Claude's options, `--strict` with optional ids (`--strict MOD-46` for the labels only) and enforcement in the module-index CI and in the CI workflow of the `mm3 new-module` scaffold. Later the same day the user changed their mind: "Ok let's leave it as warning".
- Workaround: none needed for the modules that exist. For a new module, run `mm3 module check` and read the warnings (CORE-310, since Core 0.39), which does not fail the check.
- Expected / proposed (as written, not adopted): `mm3 module check --strict [ID,…]` turns warnings into failures, all of them or only those of the named checks; `--strict MOD-46` is the label check (a field without a `title` or `description`, or whose key is missing from a shipped catalog, fails); the module-index CI and the scaffold's `.github/workflows/check.yml` run it. It was written as CORE-381 (Core 0.41, section 10.2, milestone 7, extending CORE-281 and CORE-310 without changing them) and MOD-99 changed (Contract rev 16). Precedent: CORE-207 `mm3 check-config --strict`.
- Requirements: none adopted. CORE-381 and the change of MOD-99 were written into the live specs as Core 0.41 and Contract rev 16 and spec sync PR #107 was opened; none of it reached main. The number CORE-381 was later given to ENH-007 (Core 0.41). Related: CORE-281, CORE-310, MOD-46 (the MUST), MOD-95, MOD-99, CORE-121, CORE-207 (precedent), ISS-003.
- Spec check: 2026-11-13, Core spec 0.40 and Module Contract 1.0 rev 15. Read CORE-281, CORE-310, CORE-207, MOD-46, MOD-95, MOD-99, CORE-121 and the 10.6 index CI bullet. Not checked: the implementation plan and the code of `modcheck` and of the scaffold in full. Found: MOD-46 is a MUST in the Contract (the label of every field is a catalog key); since Core 0.39 `mm3 module check` reports a missing label key only as a warning (SHOULD, CORE-310), so a module can still be compliant without labels; MOD-99 requires each index release to pass `mm3 module check` but says nothing on warnings; CORE-207 already defines `--strict` for `mm3 check-config`. Result: confirmed as a spec gap: nothing in the specs lets a missing label fail the check for a new module, so the guarantee the user wanted does not follow from MOD-46 as it is checked today. The user decided to accept that.
- Status: rejected — the user decided on 2026-11-13 to leave the label check as a warning. Spec sync PR #107 closed unmerged; Core 0.41 and Contract rev 16 reverted in the live documents (Core 0.40 and Contract rev 15 were current again), so main, the masters and the rules agreed; rules 1.59.
