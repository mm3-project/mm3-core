# ISS-013 — The audio entry is greyed out in the admin although the kiosk agent is connected
- Reported: 2026-11-12
- Type: issue (the kiosk agent is connected and reports a sink, so the spec says the audio controls are offered; see Spec check; the user can change this)
- Priority: P2 (proposed by Claude: the user gave none; a workaround exists, the YAML view and the `audio` block; the user can change it)
- Area: admin UI (audio entry of the Form view, volume and mute controls), kiosk
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: "I have audio speakers connected but in admin the audio entry is greyed out" (as reported). The user then said it is the `audio` entry in the sidebar (of the Form view). Not stated: whether the volume slider and mute toggle beside the kiosk status work, and the sidebar state of the other entries (in the screenshot of ISS-012 the sidebar lists engine, display, audio, layout, pages, backup, then the module instances; `backup` was also greyed out earlier, see below).
- Evidence from the user's system (2026-11-12): `mm3.service`, `mm3-kiosk.service` and `mm3-installer.service` are active. `GET /api/v1/kiosk` returns `connected: true`, cage 0.2.0, Chromium started with 0 restarts, one audio sink `alsa_output.pci-0000_00_1f.3.analog-stereo` ("Built-in Audio Analog Stereo", kind analog, available), applied sink with volume 40, mute false, `matched: true`, `mismatch: false`, `failure: null`; one output `HDMI-A-2` at 1920 × 1080, 60 Hz; `display.applied`, `viewport` and `dpr` are null.
- Workaround: edit the `audio` block in the YAML view.
- Expected / proposed: with the agent connected, the `audio` entry is active; the sink is a dropdown of the reported sinks, with `auto`, `hdmi` and `analog` first, and the volume slider and mute toggle work (CORE-306).
- Requirements: CORE-306 (kiosk controls: `GET /api/v1/kiosk`; the Form offers `audio.sink` as a dropdown of the reported sinks; `PUT /api/v1/kiosk/audio`; volume slider and mute toggle beside the kiosk status; 409 `CORE_API_NO_KIOSK` without an agent), CORE-296 (the agent applies output, volume and mute live), CORE-277 (agent reports of outputs and sinks), CORE-144 (order of the sinks). Not a spec gap.
- Spec check: 2026-11-12, Core spec 0.38 (the Module Contract, the implementation plan and the code were not checked). Searched "audio.sink", "kiosk agent" and "no kiosk agent". Found the requirements above. Result: the status route shows the agent connected with an available sink, so the conditions under which the spec offers the audio controls are met; a greyed-out entry deviates from it. Not found, so not claimed: a requirement that says when the admin greys out an entry, why it is greyed out here (the admin may read the status route in another way, for example the `display` fields being null, or an error in the page), and whether other sidebar entries are greyed out for the same reason (the user reported `backup` greyed out earlier in the chat; that report was suspended and not logged, and `mm3-installer.service` is active on this system). The first reading, that no agent was connected, was disproved by the status route.
- Status: rejected — the editing part is a duplicate of ISS-012 (confirmed: the form works once the section is in the YAML); the grey display of an absent section is not covered by the spec, so it is continued as the enhancement ENH-010 (decision of the user, who accepted Claude's recommendation on 2026-11-12)
