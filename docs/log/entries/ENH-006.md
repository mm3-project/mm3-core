# ENH-006 — Interactive visual engine (generative art and AR) driven by Kinect and camera: one feature in three parts
- Reported: 2026-11-12
- Type: enhancement (the user supplied an external design discussion and asked for the Core-level gaps it raises to be logged as one entry, because they belong to the same main functionality, even if complex)
- Priority: P3 (proposed by Claude: not stated by the user; a large, optional feature with no workaround needed; the user can change it)
- Area: new modules `mm3-visuals` and `mm3-vision`; Core (shell layers, state delivery, hardware services, security policy); presence; gestures
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: the user shared a design discussion (a ChatGPT conversation, attached in this chat as a text file, with a first part about a Processing-based engine and a second part that adapts it to the MM3 core spec) for a unified visual engine on the mirror: generative effects (watercolor, fluid, particles, trails, kaleidoscope), anchored AR effects (glasses, hats, body outlines) and hybrid effects, composed as scenes of layers, driven by a Kinect v1 and a USB camera, with gestures to select effects, and present in a background and a foreground plane around the MM3 widgets. The user then asked to log the Core-level needs as one entry. Hardware named in the discussion: Kinect v1, a full HD USB camera, an Intel HD 530 GPU, Debian x86 with the Chromium kiosk under Cage.
- Workaround: not applicable (new capability). The mirror runs without it.
- Expected / proposed: one feature, three parts, to be defined together in the defining phase:
  1. **Layered rendering surfaces.** A module can draw in a background and a foreground plane (the discussion proposes either two instances of the same module, or one instance with several transparent surfaces at their own z, sharing one GPU context). Core already offers two full-grid presets at z −100 and +100; whether a module with several surfaces is needed is to be decided.
  2. **High-frequency state delivery.** Hand and body positions at 20–30 Hz from a sensor to the browser, with only the latest value kept (coalescing). The discussion proposes compact JSON first and a binary stream only if profiling needs it.
  3. **Hardware-service contract.** A way for an external native or separate sensor service (Kinect, camera, tracking, gestures) to report presence, gestures and health to the engine, without Kinect-specific code in Core. The discussion proposes a Unix-socket service `mm3-vision`, a module `mm3-visuals` with a WebGL2 renderer in the browser, and `mm3-presence` as the only owner of presence and display power.
     - **Device ownership and a local frame feed (proposal of 2026-11-14, not decided).** The Media service (milestone 8: a local V4L2 camera source, the Kinect model among its open questions) and `mm3-vision` both want cameras, and a camera device can be opened by only one process at a time. Proposed: keep the two services separate, with one owner per device declared in the config and checked by the core at startup (a device with two owners is an error shown in the admin). The owner can offer a small low-resolution feed of the device (for example 320×240 at 15 to 30 fps) to other local consumers over a Unix socket, with no network and no storage, so the camera is decoded once. Likely split (as first proposed on 2026-11-14, superseded on 2026-11-19, see below): Media owns the USB camera (it already runs ffmpeg) and vision may read its feed; vision owns the Kinect (depth needs its native drivers) and may offer the Kinect colour image to Media over the same feed. **Scopes and revised split (the user's definition of 2026-11-19, still a proposal for milestone 8):** Vision gives sight to the modules through the Kinect and the camera (capture, tracking, gestures); Media provides media playback to the screen. Under these scopes the cameras are sensors, so `mm3-vision` is the default owner of both the Kinect and the USB camera, and Media is a consumer of the owner's local low-resolution feed when it needs a live camera view (a mirror camera, a doorbell, a video call). Reasons: the owner should be the service that sets frame rate, exposure and latency for tracking; tracking does not depend on Media's availability or on its full-screen takeover; sensor frames stay out of the service whose job is to serve video (the same reason merging was rejected); one rule for both sensors (Vision captures, Media plays). The per-device owner in the config still lets a setup without `mm3-vision` give the USB camera to Media. Merging the two into one process was considered and rejected: it would put native sensor drivers (libfreenect, possibly OpenNI/NiTE2 with its licence problem) and real-time tracking into the media service planned in the core, and the privacy rule "no frames leave the machine" into the same process as a service whose job is to serve video. To be settled in the defining chat of milestone 8, together with the rest of this part; the first defining chat of the vision stage 3 is a consumer of it.
     - **Camera ownership decided (the user, 2026-11-19).** The cameras are owned by Vision by default; when Vision is not present, Media can own the camera. The rule is specified in the vision defining phase in this Project (stage "Defining A: devices" of the plan below), not in the defining chat of milestone 8, which consumes it. Still open there and listed in the plan: whether Media may also take the Kinect without Vision (proposed: no, only the USB camera), and whether Media may show the local feed on LAN browsers (proposed: kiosk only).
  Points to settle when it is defined: whether Core needs any change at all or an ordinary module plus an external service is enough (the discussion itself recommends starting that way); the camera policy (see Spec check: Core denies the camera to pages); body gestures and their relation to the touch gestures of CORE-276; the renderer technology (WebGL2 in the shell against p5.js or a separate process); the vision service language (the discussion proposes C++; Claude suggested starting in Python behind the same socket contract); skeleton tracking on a Kinect v1 (needs OpenNI2 with NiTE2, whose licence and age conflict with the dependency policy) against hands and head from depth plus MediaPipe; whether tracking runs in the browser; the GPU budget of the HD 530 and an adaptive quality rule; the calibration for AR on a two-way mirror (the viewer's eye position), which Claude suggests deferring; privacy (no frames stored or sent off the machine); the scene format and the admin editing of scenes; the proposals of the discussion as a framework or library choice need a proposal before adoption.
- Requirements: none: spec gap. Related, likely to be extended or changed: CORE-92 (presets, `fullscreen_below` and `fullscreen_above` at z −100 and +100), CORE-26 (payloads ≤ 256 KiB), CORE-276 and CORE-260 (shell input frames and the touch swipe), CORE-63 (Permissions-Policy denies the camera), CORE-98 (preview placeholder for camera modules), and the `mm3-presence` reference module (replaceable presence source, generic suspend and resume hooks).
- Spec check: 2026-11-12, Core spec 0.38 (searched through the Claude Docs reader; the Module Contract and the implementation plan were not checked; the code was not checked). Searched "Kinect", "fullscreen_below", "gesture", "256 KiB" and "camera". Found:
  - "Kinect": no hit. No requirement on a depth sensor, skeleton, hand or face tracking.
  - CORE-92: `fullscreen_below` and `fullscreen_above` cover the whole grid at z −100 and +100; every other preset has z 0. So two planes around the widgets already exist as presets. The statement in the discussion that overlapping instances at different z are supported matches this.
  - CORE-26: payloads MUST be JSON-serialisable and ≤ 256 KiB. This matches the discussion.
  - CORE-276 and CORE-260: the only gestures are touch gestures sent by the shell (`swipe_left`, `swipe_right`, `tap`; a swipe is a single-pointer touch gesture with distance and time limits). Nothing on body or hand gestures.
  - CORE-63: every response sends a Permissions-Policy that denies the camera, microphone and others. A page that opens the camera (for tracking in the browser) would need this changed; the discussion does not mention it.
  - CORE-98: in preview mode, modules with sensitive content such as the camera SHOULD render a placeholder.
  - Presence: `mm3-presence` is the backend-only reference module; the engine keeps only the generic suspend and resume hooks, so presence can be replaced (camera, BLE, phone) without touching Core. This matches the discussion.
  Not checked, and so not claimed: the discussion's statements that the WebSocket coalesces queued state frames per instance, that one frontend element is created per module instance, the lifecycle table (start, stop, suspend, resume, reconfigure), `PAGE_PAUSE` and `PAGE_RESUME`, `ctx.run_blocking()`, and its section references (3–5, 6.5–6.7, 7). The discussion was written from GitHub and may refer to another version of the spec.
  Result: confirmed as a spec gap. The Core spec has the two planes (as presets) and the lifecycle for a visual module, but has no sensor input, no body gestures, no high-frequency state rule and no hardware-service contract. Part of the feature can probably be built as an ordinary module plus an external service with no Core change; the camera policy of CORE-63 is the one conflict found if tracking runs in the browser.
- Status: open (work moved to the sub-project MM3 Visuals; the Core slice stays here) — decided by the user on 2026-11-12. The sub-project owns the visuals and vision specification, rules, repositories (`mm3-visuals`, `mm3-vision`) and roadmap, as an MM3 module that follows the Module Contract; its brief is `claude/mm3-visuals-subproject.md`. This entry keeps only what needs Core: the three parts above and the camera policy of CORE-63. Any Core change the sub-project needs comes back to this log as an entry (this one, narrowed, or new smaller ones) and goes through the Core defining phase here; the Core spec stays the master. When the sub-project's first stages show what Core really needs, this entry is narrowed to those gaps or replaced by smaller entries. Changed on 2026-11-19 by the user: the vision part (`mm3-vision`, the sensor service with Kinect v1 and USB camera, tracking, gestures and presence reports) comes back to the MM3 Project and is planned here; `mm3-visuals` stays in the sub-project for now (whether it returns too is open question Q1 of the plan).
