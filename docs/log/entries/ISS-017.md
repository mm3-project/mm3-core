# ISS-017 — Intermittent failure of `test_core_361_restore_needs_the_passphrase_except_from_root` (409 instead of 202)
- Reported: 2026-11-14 (seen once in CI on PR #112; proposed to the user as ISS-017 and taken up on their "Yes")
- Type: issue (a test that gives different results on identical runs; the cause is not known; the user can change this)
- Priority: P2 (proposed by Claude: it fails a required CI job at random and a re-run clears it, so it is not blocking; the user can change it)
- Area: CI, tests (`tests/test_backup.py`)
- Spec versions at report: Core spec 0.41, Module Contract 1.0 rev 15
- Description: `test_core_361_restore_needs_the_passphrase_except_from_root` failed once in CI on PR #112 (job `test (3.11)`): the restore request answered 409 where the test expects 202. PR #112 touches no backup file, and the job passed on re-run.
- Workaround: re-run the failed job.
- Expected / proposed: the test gives the same result on every run. Done in PR #120 (see History); cause found on 2026-11-14.
- Requirements: CORE-361 (a restore always needs re-authentication, except from a root peer) and CORE-355 (409 when an operation is already running). No spec change known. A possible reading is an installer operation left over from, or running beside, another test, but that is not claimed.
- Spec check: 2026-11-14, Core spec 0.41 and Module Contract 1.0 rev 15. Read only the text of CORE-361 and CORE-355. Not read: the test, the installer fake it uses, the code of the restore route.
- Status: in progress — code: PR #120 (branch `fix/iss-017-restore-busy`), squash-merged 2026-11-14 (85947dc). The user decides when it is fixed; if the test fails again, reopen.
- Resolved in: —
- History:
  - 2026-11-14: cause found and fixed in PR #120. The installer cleared its running flag only after the final state (`done`, `failed`, `rolled_back`) was saved, logged and cleaned up, so a client that read the final state and sent the next request at once got 409; in the test it was the second restore, from root. `_step` now frees the installer when it sets a final state (guarded: only if the operation is still the running one), and the pruning of old venvs runs before the final `done` step. Test `test_core_355_the_installer_is_free_when_an_operation_is_reported_final` fails without the change; backup tests 3 runs of 66 passed; full suite 1388 passed, 92 skipped; CHANGELOG entry. The earlier reading (busy state not yet free) was right. PR #120 found squash-merged (85947dc, 13:00 UTC); status set to in progress
  - 2026-11-14: seen on PR #112 (job `test (3.11)`, 409 instead of 202), cleared by a re-run; proposed to the user as ISS-017 with P2; logged on the user's "Yes"; no cause analysis yet
  - 2026-11-14: seen again locally while PR #119 was prepared: in the first full-suite run (Python 3.14, browser tests skipped) the test failed at its last request (the restore from root answered 409, line 984), and the next full run and a run of the test alone passed; on a clean main (stash) the suite passed once. So the fault shows when the second restore starts right after the first one is reported done: the installer's busy state may not be free yet. A reading, not verified. Planned as step 1b of the milestone 7 closing plan
  - 2026-11-14: note after ENH-002 (PR #115): the installer's `busy` now also covers a waiting system action (CORE-382); this was added after ISS-017 was seen (PR #112) and does not explain it, but it is one more reason a 409 can appear in the restore tests; not investigated
