# ISS-003 — Admin editor shows internal parameter names instead of labels in the selected language
- Reported: 2026-11-07
- Type: issue (as reported by the user, who called it a "minor issue"; the cause is a conflict between the two specs, see Spec check, so it goes through the defining phase before any code)
- Priority: P2 (proposed by Claude from the user's word "minor": mildly annoying, not blocking; the user can change it)
- Area: admin UI (Form view), modules, internationalisation; specs (Core spec and Module Contract)
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: "the modules show internal parameter names rather than the selected language label in the admin editor" (as reported). Asked which modules and languages, the user answered "all of them all languages": every module, every language. The user then pasted catalogs. Clock, Italian: the entries `HEADER` ("Orologio"), `CFG_DISPLAY` ("Visualizzazione") and `CFG_DISPLAY_HELP` ("Digitale, analogico o entrambi"). Weather, English, from `~/mm3-core/modules/mm3-weather/src/mm3_weather/locales/en/LC_MESSAGES/messages.po`: as pasted, `HEADER` ("Weather"), `WEATHER_CLEAR` and `WEATHER_CLEAR_NIGHT`, with no configuration keys in what was pasted (the paste may be partial). Not stated: which tab of the editor (the Form tab is the one that shows labels, CORE-310).
- Workaround: not stated
- Expected / proposed: labels of the module parameters in the language of the admin session, instead of the internal names (to be confirmed by the user). Decision of the user, 2026-11-07, on Claude's recommendation: one master convention, the Module Contract's (option A below). Each field's `title` and `description` in the Pydantic model hold catalog keys (MOD-46, for example `title="CFG_DISPLAY"`), and the admin form reads them; the path-derived keys `CONFIG_<PATH>_LABEL` and `_HELP` of CORE-310 are dropped. The options were: A (decided): the form reads the schema `title` and `description` as catalog keys; B: modules change to the CORE-310 names, which would change a MUST of Module API 1.0 and every module's catalog; C: both supported with a defined order. Reasons given for A: MOD-46 is already a MUST in API 1.0 and the clock follows it; the key sits next to the field and is in the JSON schema the form reads, and `mm3 module check` can verify it; path-derived keys are awkward for nested fields and list items such as `zones[].label` (CLK-03). Cost noted: every field needs an explicit `title` and `description`. Settled in Core 0.39 (CORE-310 changed): the engine's own models use the same mechanism with core catalog keys `CFG_<SECTION>_<FIELD>` and `CFG_<SECTION>_<FIELD>_HELP`; nested models and list items take the `title` and `description` of their own model; a missing label shows the field name and a missing help shows nothing; `mm3 module check` reports a missing `title`, `description` or catalog key as a SHOULD, and mm3-core CI fails on it for the engine's models and the reference modules (the user's choice of 2026-11-13). The Module Contract needed no change (MOD-46 already says this). Code check of 2026-11-13 (PR D): the clock, weather, presence and greeting catalogs already had every key, so the earlier note that the clock's fields (`show_seconds`, `time_format`, `show_date`, `date_style`, `show_week`, `timezone`, `zones`) and the weather and other modules still lacked labels was stale; what was missing were the labels of the engine's own models, which PR #106 adds. For new modules the SHOULD does not force labels; a strict check was proposed (ENH-011) and the user decided to leave it as a warning.
- Requirements: MOD-46 (Module Contract: field `title` and `description` MUST be catalog keys, so the form view is translated), the master. CORE-310 changed in Core 0.39 to follow MOD-46. Related: CORE-264 (lookup along the locale chain), MOD-61 (no literal strings, including config field titles), ENH-011 (strict check for new modules, rejected).
- Spec check: 2026-11-07, Core spec 0.38 and Module Contract 1.0 rev 15. Searched in the core spec "CORE-310:", "CORE-264:", "_LABEL", "CFG_DISPLAY" and "CFG_" (the last only brought up the `CORE_CFG_*` validation codes, CLK-02, WTH-02 and other requirements, none about form labels); in the Contract "_LABEL", "CFG_", "title" and "MOD-67". Not checked: the implementation plan, the code (so it is an assumption, consistent with what the user sees, that the form implements CORE-310), the clock's Python model (whether it sets `title="CFG_DISPLAY"`), CORE-309 and CORE-101 in full. Found:
  - Core spec, CORE-310: labels and help come from the catalog of the module that owns the model, keys `CONFIG_<PATH>_LABEL` and `CONFIG_<PATH>_HELP`, `<PATH>` being the field path in UPPER_SNAKE with nested names joined by `_`. A missing label shows the field name and a missing help shows nothing, and `mm3 i18n check` does not require them. It does not mention the schema `title` and `description`.
  - Module Contract, MOD-46: field `title` and `description` MUST be catalog keys, so the form view is translated (core 6.4). Its examples use the `CFG_<NAME>` pattern: the weather config has `title="CFG_LAT"` and `title="CFG_LON"`, and the greeting module has `title="CFG_NAME", description="CFG_NAME_HELP"` with the catalog entries `CFG_NAME` and `CFG_NAME_HELP`. The Contract has no text on the `CONFIG_<PATH>_LABEL` keys of CORE-310 (no hit for `_LABEL`).
  - CORE-264: a key is looked up along the locale chain in the module's catalog, then the core catalog.
  Result: the user's report is explained, and it is not a plain defect of one side. The clock's keys `CFG_DISPLAY` and `CFG_DISPLAY_HELP` follow the Contract's convention (MOD-46 and its examples). The form, as far as the behaviour shows, looks for the CORE-310 keys `CONFIG_DISPLAY_LABEL` and `CONFIG_DISPLAY_HELP`, does not find them and shows the field name, which is what CORE-310 prescribes for a missing label. So each side follows its own spec and the two specs disagree: this is a spec conflict, to be decided in the defining phase. Also, in the clock catalog as pasted only `display` has a label and a help text; the other fields of CLK-02 (`show_seconds`, `time_format`, `show_date`, `date_style`, `show_week`, `timezone`, `zones`) have none, so they would show their field names under either convention. For the weather module, no configuration keys were in what was pasted. (Corrected by the code check of 2026-11-13: the full catalogs of the reference modules are complete; only the pasted extract was partial.)
