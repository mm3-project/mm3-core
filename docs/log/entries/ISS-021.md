# ISS-021 — `.mo` check fails when the build used another Babel release
- Reported: 2026-11-28 (found by Claude on PR #168, logged on the user's "yes")
- Type: issue (the code is stricter than CORE-263; not a spec gap)
- Priority: P1 (proposed by Claude: the five required jobs "Reference module" fail on every pull request, so nothing can be merged; the user can change it)
- Area: `mm3-build/src/mm3_build/catalogs.py` (`check_locales`), CI jobs "Reference module mm3-*" (CORE-289)
- Spec versions at report: Core spec 0.58, Module Contract 1.0 rev 17
- Description: on PR #168 (documentation only) the jobs "Reference module" of mm3-clock, mm3-weather, mm3-greeting, mm3-presence and mm3-media failed with `FAIL MOD-62 [static] …/messages.mo does not match its .po; run mm3 i18n compile` for every locale. The same commit of main (d1d9526) was green on 2026-11-23. Babel 2.19.0 has been released since; `uv.lock` pins 2.18.0. The module wheel is built in an isolated build environment, which takes the newest Babel that `mm3-build` allows (`babel>=2.15,<3`), while the check runs with the locked 2.18.0 and compares the `.mo` byte for byte. Two differences were found: the header line `Generated-By: Babel <version>`, and, for `it`, `es` and `fr`, the `Plural-Forms` header, which Babel takes from its CLDR data when the `.po` declares none (2.19.0 gives these locales three plural forms). No shipped catalog has a plural entry, so nothing a mirror shows changes.
- Workaround: none in CI (a re-run fails the same way).
- Expected / proposed: the check compares a `.mo` by its messages, not its bytes, ignoring the `Generated-By` line, so the Babel release that compiled it does not count; and the catalogs of the reference modules declare `Plural-Forms` as the core catalogs do, so the compiled header does not depend on Babel's CLDR data.
- Requirements: CORE-263 (Core spec 0.15, §8.5 Catalogs at run time), CORE-280 (Core spec 0.17, §10.2). The failure is reported under MOD-62 by `mm3 module check`. No spec change.
- Spec check: 2026-11-28, Core 0.58, Contract 1.0 rev 17. Read CORE-263 ("fails when one is missing or does not match its `.po`"), CORE-280 and MOD-62. CORE-263 does not require byte equality: a comparison by content meets it. Confirmed: a deviation of the code (too strict), not a spec gap. Not checked: the implementation plan.
- Status: in progress
- Resolved in: —
- History:
  - 2026-11-28: found on PR #168; cause found (Babel 2.19.0 in the build environment against 2.18.0 in the lock; `.mo` bytes differ in `Generated-By` and, for it/es/fr, `Plural-Forms`); proposed to the user as ISS-021 with P1 and two fixes (compare by content; or pin Babel for the build); the user chose to compare by content.
  - 2026-11-28: the comparison by content alone left `it`, `es` and `fr` failing (the `Plural-Forms` header from CLDR); proposed to the user to declare `Plural-Forms` in the 25 `.po` files of the five reference modules, as in the core catalogs; the user agreed. The test fixture `tests/module_projects.py` gets the same header. Not extended yet: the `mm3 new-module` scaffold, which writes `.po` files without `Plural-Forms` (asked to the user). Fix in its own PR, with PR #168 stacked on it.
