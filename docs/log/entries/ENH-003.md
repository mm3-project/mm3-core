# ENH-003 — Colour of the UI elements cannot be set, only opacity
- Reported: 2026-11-07
- Type: enhancement (as reported by the user)
- Priority: P3 (set by the user: "low pri"; on the enhancement scale "maybe in the future")
- Area: core, admin UI, appearance (theme)
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: "allow to define not only brightness opacity of ui elements displayed on the mirror but also color" (as reported). Read as the per-instance `appearance.opacity` (0–1) being the setting the user means by "brightness opacity"; if the user means something else, such as the display brightness of the presence module, this has to be corrected. Not stated: whether the colour is wanted per instance, per element inside a widget, or for the whole mirror; which colours (text, background, accent); where it should be set (the Layout overlay toolbar, the Form view, the YAML).
- Workaround: not stated by the user. The spec allows colours to be changed by writing CSS (see Spec check), which is not a setting in the UI and was not verified in practice.
- Expected / proposed: a way to define the colour of the UI elements, next to the opacity, as a setting (to be specified by the user). Points to settle when it is defined: the scope (the whole mirror, an instance, an element of a widget); whether it is a new `appearance` field, a theme setting, or controls in the Layout overlay toolbar (CORE-328); free colours or only the theme tokens (WGT-11 allows only the tokens good, warning, critical, accent and muted for an element's `color`); contrast and legibility on the mirror; how it fits the rule that colours come from the theme variables (CORE-261) and that the list of those variables is part of the Module API (Contract MOD-33).
- Requirements: none: spec gap. Related, likely to be extended or changed: CORE-246 and CORE-328 (the `appearance` object and the overlay toolbar), CORE-261 (theme variables, colours), CORE-262 (`custom.css`), CORE-214 (`appearance.css`), WGT-11 (element colour tokens).
- Spec check: 2026-11-07, Core spec 0.38 (the Module Contract and the implementation plan were not checked, apart from the Contract's MOD-33 as cited by CORE-261). Searched "opacity", "CORE-214:" and "color", and read the table of the `appearance` fields. Found:
  - `appearance` (CORE-246, the table of the instance config) has the fields `scale` (0.5–3.0), `align` and `valign`, `opacity` (0–1, default 1), `overflow`, `header`, `classes` and `css` (CSS scoped to the instance's shadow root, limits in CORE-214). There is no colour field.
  - CORE-328: the overlay toolbar sets `appearance.scale`, `align`, `valign`, `opacity`, `overflow` and `header`, and has no colour control.
  - CORE-261: the shell defines the theme variables on `:root`: colours `--mm3-color-bg`, `-fg`, `-bright`, `-dimmed`, and the state tokens `-good`, `-warning`, `-critical`, `-accent`, `-muted`. The list is part of the Module API (Contract MOD-33).
  - CORE-262: the optional `custom.css` may set theme variables for the whole mirror or for one instance (`[data-instance="weather_home"]`) and is a history section; it cannot reach inside shadow roots.
  - WGT-11: an element of a widget may set `color` in a rule's `style`, only as one of the theme tokens good, warning, critical, accent, muted.
  Result: the user's assumption is confirmed: opacity is a setting (a field and a toolbar control) and colour is not. Colour can be changed only by writing CSS: theme variables in `custom.css`, for the mirror or for one instance, or the instance's `appearance.css`. Not checked: whether the admin UI offers an editor for `custom.css` (it belongs to the config set, CORE-262, but the tabs of CORE-322 do not name it) and whether the variables override as the spec says.
- Status: open — to go through the defining phase before any code, when the user decides to act on it
