# ISS-015 — Intermittent failure of the weather test `test_wth_11_sent_after_every_refresh_whatever_the_view`
- Reported: 2026-11-13 (found by Claude on PR #101; logged on the user's "ok" to Claude's proposal of the same day)
- Type: issue (a test, or the module, that gives different results on identical runs; the cause is in the test kit, see History; the user can change this)
- Priority: P2 (proposed by Claude: it fails the required job "Reference module mm3-weather (CORE-289)" at random and a re-run clears it, so it is not blocking; the user can change it)
- Area: CI, tests (`modules/mm3-weather/tests/test_module.py`), possibly the weather module's refresh scheduling or the test clock (`mm3.testing`)
- Spec versions at report: Core spec 0.40, Module Contract 1.0 rev 15
- Description: the CI job "Reference module mm3-weather (CORE-289)" failed on PR #101 (run 43459618685, job 132002727561, Python 3.13): `assert len(h.notifications.of("WEATHER_CURRENT")) == 3` gave `2 == 3` (line 135). The test starts an `hourly` instance with `refresh: 300`, advances the virtual clock by 10 minutes and expects one notification at start and one after each refresh (3). The other 121 tests of the module passed. Run alone on the development machine, the test failed once in three runs (0.6 s each), so the fault is in the test or the module, not in PR #101, which changes no file under `modules/` or `src/mm3/testing`.
- Workaround: re-run the failed job (done on 2026-11-13: the re-run passed and #101 was merged).
- Expected / proposed: the test gives the same result on every run: either the second refresh at exactly 10 minutes always runs before the assertion (a deterministic clock step, or advancing a little past the boundary), or, if the module can skip a refresh at the boundary, the module is fixed. Not decided: which of the two it is. (2026-11-14: the cause found for ISS-016 is in the test kit and fits this symptom: a job due exactly at the end of `advance()`; the kit is fixed, see History.)
- Requirements: WTH-11 (with `emit` on, every instance sends `WEATHER_CURRENT` after each successful refresh), WTH-02 (`refresh` is a duration, at least 5 min, so 300 s is valid). Related: ISS-014 (an earlier timing flake, in `test_mod_06_kv_writes…`), ISS-016 (same cause), CORE-278 (virtual clock of the kit). Not a spec gap as far as read; no spec change expected.
- Spec check: 2026-11-13, Core spec 0.39 (the Module Contract, the implementation plan and the module code were not read; the harness `advance` was read only for its signature and docstring). Searched "WTH-11" and read WTH-11 and WTH-02. Found: WTH-11 as above, which says nothing on what happens when a refresh falls exactly on the end of an `advance`. Result: the expected count of 3 is consistent with WTH-11 (start plus two refreshes at 5 and 10 minutes), so a run that gives 2 is the unexpected one. Not found, so not claimed: whether the lost notification is the refresh at exactly 10 minutes (boundary of the virtual clock) or one at the start, and whether the cause is the test, the harness clock or the module. On 2026-11-14 the module code and the scheduler were read: the refresh is `scheduler.every(refresh, start_now=True)` with no jitter, and the notification is sent after the storage write; the module has no fault found.
- Status: in progress — code: PR #110 (branch `fix/iss-015-iss-016-flaky-tests`), squash-merged 2026-11-13 (025e9f7). It is expected to fix this test through the kit change of ISS-016, but that is not proved: the failure was seen only twice and never captured. The user decides when it is fixed; if it fails again after #110, reopen.
