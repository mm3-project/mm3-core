# ISS-016 — Two more intermittent tests: `test_prs_05_days_are_start_days` and `test_core_377_history_survives_a_reload_until_save_or_discard`
- Reported: 2026-11-14 (first seen on 2026-11-13 on PR #108 and PR #109; proposed to the user as ISS-016 and taken up on their "Both")
- Type: issue (tests that give different results on identical runs; the first has a cause in the test kit, the second in the test itself; the user can change this)
- Priority: P2 (proposed by Claude: both fail required CI jobs at random and a re-run clears them, so they are not blocking; the user can change it)
- Area: CI, tests (`modules/mm3-presence/tests/test_module.py`, `tests/test_admin_editor.py`), test kit (`src/mm3/testing/loop.py`)
- Spec versions at report: Core spec 0.40, Module Contract 1.0 rev 15
- Description: (1) `test_prs_05_days_are_start_days` failed once in CI and once in three local runs on PR #108 (`assert h.suspended` false after `advance(to="2026-10-31T23:00:00+01:00")`); (2) `test_core_377_history_survives_a_reload_until_save_or_discard` failed 1 run in 8 on main without the PR's change while PR #109 was developed (line 790: the Redo button is not enabled right after a second reload), and once in a full suite.
- Workaround: re-run the failed job.
- Expected / proposed: both tests give the same result on every run. Done in PR #110 (see History).
- Requirements: CORE-278 (one engine clock, virtual in `mm3.testing`: the scheduler, `asyncio.sleep`, budgets and `ctx.now()` move together), PRS-05 (days are start days, the schedule fires on its start day), CORE-377 (the draft history survives a reload). No spec change.
- Spec check: 2026-11-14, Core spec 0.40 and Module Contract 1.0 rev 15. Read CORE-278 and MOD-28 (the kit's virtual clock). Not re-read: PRS-05 and CORE-377 (taken from the test names and the earlier entries), the implementation plan. Found: CORE-278 says the virtual clock is driven by `h.advance()` so that the scheduler, `asyncio.sleep`, budgets and `ctx.now()` move together; nothing on a job due exactly at the end of an advance. Result: not a spec gap; the kit does not do what CORE-278 describes in that case (a job that falls due at the target does not run).
- Status: in progress — code: PR #110 (branch `fix/iss-015-iss-016-flaky-tests`), squash-merged 2026-11-13 (025e9f7). The user decides when it is fixed.

- History:
  - 2026-11-13: seen on PR #108 (presence test) and on PR #109 (CORE-377 test), noted in the round 1 plan and proposed to the user as ISS-016; not logged yet
  - 2026-11-14: logged on the user's "Both" (answer to "ISS-016 or ISS-015"); priority P2 proposed
  - 2026-11-14: causes found. (1) Presence: reproduced, 13 failures in 190 runs. In a failing run the job planned for 23:00 on Saturday is one float rounding (about 1e-11 s) after the target of `advance(to=…)`. `LoopClock` starts at the real monotonic time, so two times computed in different steps can differ by an ulp. The scheduler waits for that remainder, asyncio runs the timer at once (it is inside its clock resolution), the virtual time does not move, and the scheduler waits again until the settle rounds run out: the job never runs. The log of the clock waits in a failing run showed the same wait of 1.5e-11 or 2.9e-11 s repeated at an unchanged time. (2) CORE-377: reproduced, 9 failures in 24 runs. The page draws the Undo and Redo buttons before `draft.load()` has restored the stored history, so the test saw a disabled Redo; a test race, the page is correct (the same for the two keypresses that follow: they were sent before the restore). Not caused by any code of ISS-001 or ENH-004
  - 2026-11-14: code written (PR #110): `LoopClock.wait` and `sleep` round a wait shorter than 1 µs (not zero) up to 1 µs, and `advance()` runs a timer up to 2 µs past its target (`_QUANTUM`, `_DUE_TOLERANCE`; waits of 1 µs or more are unchanged); the CORE-377 test waits for the enabled Redo button and for each redo step. Test `test_core_278_advance_runs_a_job_one_float_rounding_past_the_target` (fails without the change). Result: presence test 0 failures in 70 runs (about 7 % before); CORE-377 test 0 in 60 (9 of 24 before); full suite 1421 passed, 2 skipped; the four reference-module suites pass; ruff, mypy and spec references (0 stale) clean; a first version of the kit change (tolerance only) was not enough, the failing run still spun on the tiny wait, which led to the rounding of waits. Status set to in progress. Note: the CHANGELOG says the weather test (ISS-015) is expected to be fixed by this and not proved
