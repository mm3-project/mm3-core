# ISS-008 — Undo goes back only one change instead of through the history up to the last saved version
- Reported: 2026-11-12
- Type: issue (the user did not name a type; the first spec check found the behaviour already required, see Spec check, so Claude typed it as an issue; the code check of 2026-11-13 located it in the section undo of CORE-152, whose repeated use the spec does not define, so it now needed a spec clarification before the code; the user can change this)
- Priority: P2 (the user said "pri low" and "no workaround". On the issue scale P3 means a workaround exists and P1 blocking, so Claude mapped "low, no workaround" to P2, mildly annoying and not blocking; the user can change it)
- Area: admin UI, editor (section undo, "Undo last change here")
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: "undo should support undo up to the last saved version. currently is just last change." (as reported). On 2026-11-13 the user confirmed that the control concerned is the section undo, "Undo last change here" (CORE-152), not the general Undo button or Ctrl+Z.
- Workaround: none (as stated by the user). Since 2026-11-13 known: the general Undo button in the tab bar, or Ctrl+Z, walks back every step of the draft (CORE-151); it does not limit itself to one section. Discarding the draft returns to the saved version at once, but loses every change.
- Expected / proposed: defined in Core 0.39 (CORE-152 changed), as proposed: a step made by "Undo last change here" is marked as a revert of the step it undoes; each press reverts the latest step touching that section that is neither a revert nor already reverted, so repeated presses walk back through the section's earlier steps to the start of the draft history (CORE-377, ENH-004); the control shows the label of the step it would revert and is disabled when there is none; the undo and redo of CORE-151 treat reverts as ordinary steps, and a revert undone there makes its step revertable again. A later ordinary edit of the section becomes the newest step to revert, so no reset rule was needed.
- Requirements: CORE-152, changed in Core 0.39 to define repeated presses. CORE-151 checked and met (see Spec check). Related: CORE-377 and ENH-004 (the life of the log), ISS-004 (the buttons, done).
- Spec check: 2026-11-12, Core spec 0.38 (the Module Contract and the implementation plan were not checked; the code was not checked). Re-read CORE-151 by search: "The admin editor keeps one undo/redo history for the current draft, shared by layout, form and YAML views: Ctrl+Z undo, Ctrl+Shift+Z or Ctrl+Y redo, plus toolbar buttons. Each step is a JSON Patch with a readable label; at least 200 steps." Result: the user's report (undo only reverts the last change) deviates from CORE-151, which requires a history of at least 200 steps. The wish "up to the last saved version" is already covered while the draft has 200 steps or fewer; beyond 200 the spec allows older steps to be dropped ("at least"), and a limit of "all steps since the last saved version" is a change that belongs to ENH-004 (the life of the log). The spec does not say what undo does at the saved version (disabled, or a stop). Not found, so not claimed: whether the cause is the history not being kept (only one patch stored), or undo not repeating.
  Second check, 2026-11-13, Core spec 0.38, mm3-core main at be1f251 (after PR #97); read `docs/spec/core.md` CORE-151 and CORE-152, `src/mm3/core/web/adminui/draft.js` and `config.js`; ran Playwright tests in Chromium (not committed). Found:
  - CORE-151 is met: the draft keeps up to 500 steps (`MAX_STEPS`); three Layout moves, three Form edits and three YAML steps were each undone one by one with Ctrl+Z and with the Undo button, and redone with Ctrl+Shift+Z. The existing tests `test_core_151_*` pass.
  - CORE-152: `undoSection()` reverts the latest step touching the section by applying a new step ("Reverted: …"). The next press finds that new step as the latest one touching the section and reverts it, so repeated presses alternate between the last two values (de → fr → de → fr, verified). This is the "only the last change" the user sees.
  Result: the first check (deviation from CORE-151) is not confirmed: CORE-151 works. The defect is in the section undo, and CORE-152 does not define repeated presses, so it is a spec gap in CORE-152 (unclear point), not a plain deviation. The user decided on 2026-11-13 to clarify it in the Core 0.39 batch and code it afterwards.
