# ISS-007 — MQTT connection lost; no MM3 topic visible in an MQTT explorer
- Reported: 2026-11-12
- Type: issue
- Priority: P1 (set by the user: "non blocking however high pri as it is essential"; on the issue scale P1 means hindering or blocking, so this is the user's choice of urgency, not a blocking defect; the user can change it)
- Area: core, MQTT bridge (milestone 7)
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: "mqtt gives a warning core mqtt_connection_failed {"subsystem":"mqtt","reason":"lost"} in the log. I cannot see any entry for magicmirror in a mqtt explorer" (as reported). Not stated: the `engine.mqtt` settings (url, `base_topic`, `client_id`, user), which broker, whether the broker log shows the connection, whether the warning repeats, whether the admin or `mm3 diag check` says anything, the explorer's subscription (`#` or a topic), and what "magicmirror" refers to (see Spec check).
- Workaround: not stated
- Expected / proposed: the bridge connects and stays connected, and its topics are visible in an MQTT explorer (at least the retained `online` state, see Spec check). Points to ask or check when it is taken up: the exact `engine.mqtt` block (without the password); the broker's log for that client id; whether two clients use the same `client_id` (default `mm3-<hostname>`, a second client with the same id makes the broker drop the first, which looks like a lost connection that keeps repeating); the broker's access rules for the user (publish and subscribe on the base topic); the keepalive; TLS settings if `mqtts`; whether the explorer is connected to the same broker and user and subscribes to `#`.
- Requirements: CORE-339 (connection: one client, Last Will `offline` and `online` published retained on `<base>/state` after every connect, retry after 1 s doubling up to 60 s, `GET /api/v1/status` carries `mqtt: {connected, since, error}`, `mm3 diag check` reports ok, fail or skip), CORE-338 (bridge configuration; default `base_topic` `mm3/<hostname>`). Not a spec gap for the connection itself; the log event name and the `reason` values are not in the spec text found (see Spec check).
- Spec check: 2026-11-12, Core spec 0.38 (the Module Contract and the implementation plan were not checked; the code and the broker were not checked). Searched "mqtt_connection_failed" and "connection_failed" (no hit), "CORE-338", "CORE-339", "CORE-340", "CORE-341" and "reconnect". Found:
  - CORE-338: `engine.mqtt` is optional and without it the bridge is off; keys `url`, `username`, `password`, `ca`, `client_id` (default `mm3-<hostname>`), `keepalive` (10–3600, default 60), `base_topic` (default `mm3/<hostname>`), `export` and `import` (default `[]`), `ha_discovery` and others. `mqtts` verifies the certificate and host name.
  - CORE-339: one client (aiomqtt, adapter `mm3.core.services.mqtt`); Last Will `offline` on `<base>/state`, retained, QoS 1; after every connect the bridge publishes `online` there, retained; a lost or refused connection is retried after 1 s, doubling up to 60 s with ±20 % jitter; subscriptions are restored after every connect; `GET /api/v1/status` carries `mqtt: {connected, since, error}` with a short reason without credentials; `mm3 diag check` reports ok, fail (configured but not connected) or skip (off).
  - CORE-341: only notifications matching a glob of `mqtt.export` are published, under `<base>/event/<NAME>`; the default is none, and exports are dropped, not queued, while disconnected.
  Result: the report is consistent with a deviation from CORE-339, not a spec gap. If the bridge had connected, a retained `online` message would exist on `mm3/<hostname>/state` (or the configured `base_topic`) and an explorer subscribed to `#` would show it; a "lost" connection that repeats means the retry of CORE-339 is running but never reaches a stable connection. The name "magicmirror" is not in the spec: the default topic is `mm3/<hostname>`, so an explorer filtered on "magicmirror" would show nothing even when connected, unless `base_topic` was set to it. Not found, so not claimed: the log event name `mqtt_connection_failed` and its `reason` values (the spec gives the status `error` field but no event names for the bridge in what was searched), and which of the causes listed above applies.
- Status: done — on 2026-11-12 the user reported that the MQTT connection works now and the entries are visible in the explorer. No code change and no spec change were made, so "Resolved in" is empty; the cause (broker side, configuration, or the bridge) was not recorded. If it was the bridge, this entry is the record to reopen. The log event name and reasons are still not in the spec (a possible minor spec point, not logged separately).
