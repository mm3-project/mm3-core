# ISS-020 — The staged upload of a restore is deleted after the final state
- Reported: 2026-11-20 (seen once in CI on PR #155, job `test (3.13)`; logged on the user's "Yes" to Claude's proposal, with the fix in its own PR)
- Type: issue (the code does not do what CORE-361 says at the moment a client can observe it; not a spec gap)
- Priority: P2 (proposed by Claude: it fails a required CI job at random and a re-run clears it; on a mirror the file is gone a moment later; the user can change it)
- Area: installer (`src/mm3/installer/backupops.py`), tests (`tests/test_installer_uploads.py`)
- Spec versions at report: Core spec 0.56, Module Contract 1.0 rev 16
- Description: on PR #155 the job `test (3.13)` failed in `test_core_361_a_restore_from_an_upload_deletes_it_when_it_ends`: after the operation showed `done`, the staged `.mm3backup` was still there. `BackupRunner.restore` deleted the staged file in a `finally` that runs after `_restore` has written the final step `done`; since ISS-017 the final state is visible as soon as it is written, so a client polling the operation can see `done` while the file still exists. The re-run passed.
- Workaround: none needed on a mirror (the file goes a moment later); in CI, re-run the job.
- Expected / proposed: the staged file is deleted before the restore shows `done`, `rolled_back` or `failed`.
- Requirements: CORE-361 (Core spec 0.45, §10.8 Backup and restore). No spec change.
- Spec check: CORE-361 read; the code differs from it, no spec gap.
- Status: in progress
- Resolved in: —
- History:
  - 2026-11-20: seen on PR #155 (job `test (3.13)`), cleared by a re-run; cause found in `backupops.py` (delete in `finally` after the final step); proposed to the user as ISS-020 with P2 and a fix in its own PR; logged on the user's "Yes". Fix: the restore deletes its staged upload just before each final step (`_release`), and still in `finally`; a new test checks that the file is gone when the final state is written, and fails without the fix.
