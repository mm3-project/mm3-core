# MM3 Issue and Enhancement Log

The reports the user makes in chat, as `ISS-nnn` (issue) and `ENH-nnn` (enhancement), with the spec versions current when each was reported and what was decided. The specs stay the authority on behaviour; this log records where each change came from. The project rules (`claude/mm3-rules.md` in the claude.ai Project "Magic Mirror 3", section "Issue and enhancement log") say when an entry is written and how it moves through the defining and developing phases.

The log moved here from the project documents `claude/mm3-issue-log.md` and `claude/mm3-issue-log-entries-1.md` … `-4.md` on 2026-11-17 (log 2.55; a process change asked by the user, not a log entry), because a project document can only be replaced whole and the log had to be split to stay readable. Here an entry is edited in place.

Current specification versions: Core spec 0.49, Module Contract 1.0 rev 16 (`docs/spec/versions.toml` is the source).

## Where things are
- `entries/<ID>.md`: one file per entry. A YAML front matter holds the columns of the table below; the text under `# <ID> — <title>` holds the details in the format of the template.
- `round-1-plan.md`: the round 1 plan agreed with the user (frozen with the move; new plans are added as files of their own).
- `HISTORY.md`: the log history up to the move (log 1.0 to 2.55). Later changes are the git history of `docs/log/`; every commit that changes an entry names the entry ids.
- The table below is generated: after adding or changing an entry run `uv run python tools/log_index.py`. CI runs it with `--check`.

## Adding or changing an entry
1. A new entry gets the next free id of its type and the next `seq` (the order of reporting), in a new file `entries/<ID>.md` copied from the template below.
2. A change edits the entry in place: the front matter fields that changed, the body fields, and one line under History with the date. Entries are never deleted; a wrong entry is corrected and the correction noted in its History.
3. Run `uv run python tools/log_index.py`, commit with the entry ids in the message, and open a pull request (`docs/log-<ids>` branch) or add the change to the PR of the work it belongs to.

## How the log works
- **Type:** `ISS` = issue (the implementation does not do what the spec says, or a defect in the running system). `ENH` = enhancement (new or changed behaviour that the spec does not cover yet).
- **ID:** `ISS-001`, `ISS-002`, … and `ENH-001`, `ENH-002`, …, numbered separately, never reused.
- **Priority (P1–P3):** set from the report, shown with the type as `ISS P1`, `ENH P2`, and changeable by the user at any time (the change is noted in the entry's history). When the user does not state one, Claude proposes one in the entry and says so.

  | Priority | Issue | Enhancement |
  | --- | --- | --- |
  | P1 | Hindering or blocking | Major |
  | P2 | Mildly annoying, not blocking | Nice to have |
  | P3 | There is a workaround (the entry states it) | Maybe in the future |

- **Verification:** when the user classifies a report ("it is a gap", "the code is wrong", "it is an enhancement"), Claude checks it against the specs in the same turn, before settling the type and the requirement ids. It searches the Core spec and, for module behaviour, the Module Contract (and the implementation plan when the question is whether something is planned or done), and records in the entry's **Spec check** field the date and spec versions, what was searched, which requirement ids were found, what was not checked, and the result: confirmed, or not confirmed with what the spec does say. If the check contradicts the user's assumption, Claude says so plainly, corrects the entry (requirement ids; spec gap or deviation from a requirement) and keeps the user's original assumption in the entry's history. If the user asks only to log, the entry says "spec not yet checked" and is checked when the user asks.
- **Status:** `open` → `in spec` (an enhancement or spec gap is being defined or written into the spec) → `in progress` (code or PR under way) → `fixed` / `done` (merged, with PR and release noted) or `rejected` / `duplicate` (with the reason).
- **Decision:** the user decides when an entry is implemented or fixed. Entries stay `open` until then; priority is an input to that decision, not an order Claude follows on its own.
- **Requirements:** for an issue, the requirement ids it violates, or "none: spec gap" if the spec is silent. For an enhancement, the requirement ids it adds or changes, once known.
- **Spec impact:** an enhancement, or an issue that shows a spec gap, goes through the defining phase first (spec edit, version bump, Document history row, spec sync PR) before any code. An issue where the code differs from an existing requirement is developed against that requirement with no spec change.
- **Source in the spec:** the Document history row of a spec change that comes from entries names them in a `Source:` part (for example `Source: ENH-003`), and the resolved entry records the spec version, the history row and the PR. Log ids are sources, not requirement ids.
- Entries are not deleted. A wrong entry is corrected in place and noted in the entry's history.
