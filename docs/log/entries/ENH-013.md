# ENH-013 — No uninstall or purge command: wiping everything to reinstall is a manual procedure
- Reported: 2026-11-15 (from the user's question "come posso cancellare tutto e reinstallare?", asked after milestone 7 was closed; logged on the user's "si aggiungi" to Claude's proposal of the same day)
- Type: enhancement (no document read describes a command that removes an MM3 installation; the Core spec text was not searched, see Spec check; the user can change this)
- Priority: P3 (proposed by Claude: the user gave none; a manual workaround exists; the user can change it)
- Area: tooling and deployment (`mm3-install.sh`, the `mm3` CLI, the installer service), specs
- Spec versions at report: Core spec 0.45, Module Contract 1.0 rev 15
- Description: "come posso cancellare tutto e reinstallare?" (as asked; the answer to Claude's question on what "post milestone 7" meant). Not stated: why the reinstall is wanted, whether the machine is a kiosk system, whether the configuration and the stored data are to be kept or lost.
- Workaround: the manual procedure given in the chat on 2026-11-15, not tested by Claude: (1) back up from `/admin/backups` and copy the archive, its sidecar and the age key off the machine; (2) `systemctl disable --now` the units `mm3-kiosk.service`, `mm3.service` and `mm3-installer.service`; (3) remove `/opt/mm3`, `/etc/mm3`, `/var/lib/mm3` and `/var/lib/mm3-install`, the unit files and the polkit rule of the installer, then `systemctl daemon-reload`; (4) optionally remove the users `mm3`, `mm3-install`, `mm3-build`, `mm3-kiosk` and the groups `mm3` and `mm3-kiosk`; (5) leave the Debian packages; (6) run `mm3-install.sh` again, set the installer passphrase and TOTP again (`sudo mm3 installer passphrase|totp`), create a new token (`mm3 token new`) and, if wanted, restore the backup from `/admin/backups`.
- Expected / proposed: a command run by root (in `mm3-install.sh`, for example `--uninstall`, or in the CLI) that stops the units and removes what the installer created, in two levels: remove the software and keep the data (configuration, state, tokens, backups), or purge everything. It would take a pre-operation backup first or say that none was taken, list what it will remove and ask for a confirmation, never touch the Debian packages and never run from the engine or the installer service (CORE-353, CORE-368: only a root peer may change the installation). Points to settle when it is defined: script or CLI; whether the backup archives and the age key are kept by default; whether the users and groups are removed; what happens on a kiosk system (the kiosk user and the audio session); the exit codes.
- Requirements: none: spec gap, as far as read (not confirmed, see Spec check). Related: CORE-293 (`mm3-install.sh`), CORE-353, CORE-357 (installer service and its unit), CORE-359, CORE-366 (pre-operation backups), CORE-368 (users `mm3-install` and `mm3-build`), CORE-290..292 (units), CORE-143 and CORE-268 (kiosk unit and groups).
- Spec check: 2026-11-15, Core spec 0.45 and Module Contract 1.0 rev 15, partial. Searched the project documents (rules 1.70, the issue log index and its entry parts) for "uninstall purge reinstall mm3-install.sh remove /opt/mm3": the hits describe `mm3-install.sh` as idempotent and never overwriting configuration, env file, state or tokens, the installer's write paths, and the removal of a module (`mm3 modules remove`, CORE-358); none describes removing an installation. Not searched: the text of the Core spec (the document was opened but its text was not read in this turn), the Module Contract, the implementation plan, the code of `mm3-install.sh`. So a gap is likely but not confirmed. The paths in the workaround come from the rules and were not checked on the machine; the locations of the env file, the unit files and the polkit rule are not stated in the documents read.
