# MM3 Project Rules

Version 1.79 — 2026-11-20. Maintained by Claude; updated whenever a spec change affects these rules, with an entry in the change log at the end. This file, `docs/rules.md` in mm3-core, is the master since 2026-11-17; the claude.ai Project document `claude/mm3-rules.md` only points here. A change to the rules is edited in place and goes through a pull request like any other file (with the spec sync PR when a spec change causes it); the change log below and the git history of this file record it. A chat that has no clone reads the rules on main at https://raw.githubusercontent.com/mm3-project/mm3-core/main/docs/rules.md and the log at https://raw.githubusercontent.com/mm3-project/mm3-core/main/docs/log/README.md.

## Session start
At the start of every new chat in this project, before any other work, ask two short questions (skip any the user's first message already answers):

1. **Area:** which part of MM3?
   - Core engine (mm3-core: engine, shell, admin UI, built-in services) — say which milestone of the implementation plan
   - A module (name, new or existing; kind: full, backend-only, front-end-only; target API version)
   - A widget or widget template for mm3-widget
   - Tooling (mm3 CLI, mm3 migrate, mm3 module check, mm3.testing, mm3-build, installer)
   - Catalog / module index, packaging, CI, deployment, dependency maintenance
   - Specs and documentation only
2. **Phase:** defining (requirements and spec changes) or developing (code against the current spec)?

Then:
- Read the implementation plan's tracker and the section of the milestone in progress.
- Read the log table in `docs/log/README.md` of mm3-core main and name the open entries that touch the session's area; read an entry's details only when needed, from `docs/log/entries/<ID>.md`.
- Core or tooling work: follow the Core Engine Specification first; check the Module Contract for any effect on modules (API version, MOD rules).
- Module or widget work: follow the Module Contract first; use the core spec only for engine behaviour the module relies on.
- Defining phase: ask requirement questions, edit the specs, no code.
- Developing phase: code only against what the specs say; if the spec is missing or unclear on a point, stop and switch to defining for that point.
- Core development: check open `spec-change` issues in mm3-core and `docs/spec/coverage.md` for the milestone in progress.
- State in one line at the start which area, milestone and phase the session is in, and the spec versions in use.
- At the end of a milestone chat, update the milestone's status in the plan and in `docs/spec/milestones.toml`.

## Issue and enhancement log
- Any chat in this project (including a general Q&A chat) records a report as soon as the user makes one: a new file `docs/log/entries/<ID>.md` in mm3-core, copied from the template in `docs/log/README.md`, with the next `seq`, then `uv run python tools/log_index.py`, committed with the entry id in the message on a branch (`docs/log-<ids>`, or the branch of the work it belongs to) and a pull request (main is protected), with the next free id, the date, the type (issue or enhancement), the priority, the area, the Core spec and Module Contract versions current at that moment, the requirement ids concerned (or "none: spec gap"), the workaround if there is one, and status `open`. A question is not a report; if it is unclear whether the user is reporting something, ask in one line. The entry format is the template in `docs/log/README.md`.
- Priority (P1–P3, defined in the log): for an issue 1 = hindering or blocking, 2 = mildly annoying and not blocking, 3 = a workaround exists (recorded in the entry); for an enhancement 1 = major, 2 = nice to have, 3 = maybe in the future. The user sets it; when the user does not state one, propose one in the entry and say so.
- Verify before classifying: when the user classifies a report ("it is a gap", "the code is wrong", "it is an enhancement"), check it against the specs in the same turn, before settling the type and the requirement ids. Search the Core spec and, for module behaviour, the Module Contract (and the implementation plan when the question is whether something is planned or done) for the terms and the requirements involved. Record in the entry's Spec check field what was searched, which requirement ids were found and the result: confirmed, or not confirmed with what the spec does say. If the check contradicts the user's assumption, say so plainly, correct the entry (the requirement ids, and whether it is a spec gap or a deviation from a requirement) and keep the user's original assumption in the entry's history. If the user asks only to log, log with "spec not yet checked" and check when asked.
- The user decides when an entry is implemented or fixed. Until then it stays `open`; Claude does not start work on an entry on its own.
- When the user decides to act on an entry: an enhancement, or an issue that shows a spec gap, goes through the defining phase first (spec edit, version bump, Document history row, spec sync PR). An issue where the code differs from an existing requirement is developed against that requirement, with no spec change.
- The source of every change stays in the specification: the Document history row of a spec change that comes from log entries names them in a `Source:` part (for example `Source: ENH-003, ISS-007`), next to the list of requirement ids. Only requirement ids are listed as added, changed or removed; log ids are sources, not requirements. The branch, PR description and CHANGELOG entry of the code that follows cite the same entry ids.
- When an entry changes or is resolved, edit its file in place (the front matter fields and the body: status, the spec version and history row that carry the change, the PR and merge, and a line in its History), run `tools/log_index.py`, and commit with the entry ids in the message; the change can go in the PR of the work it records. Entries are never deleted. When a spec version changes, update the versions line of `docs/log/README.md` in the spec sync PR. The git history of `docs/log/` is the log history; no history table is kept any more.
- Entries are edited in place with the file tools; never rewrite the log or a whole entry from memory, and never copy the log back into project documents.
- `spec_sync.py` and `check_spec_refs.py` must not read `ISS-nnn` or `ENH-nnn` as requirement ids. The first spec sync PR that has a `Source:` part verifies this and, if the tools do, makes them ignore these prefixes in the same PR.

## Spec versioning
- Core spec: MAJOR.MINOR in its byline; any requirement added, changed or removed bumps MINOR; 1.0 = first engine release. Every change gets a row in its Document history (section 13) listing every requirement id added, changed or removed (CORE-76) and, when it comes from the issue and enhancement log, its sources.
- Module Contract: version = Module API version (1.0); each document change bumps the revision (rev N) and gets a row in its Document history (section 14), listing the MOD ids added, changed or removed and, when it comes from the log, its sources.
- When a spec changes, update its version in the same session and the current versions in this file and in the log.
- Every defining session that changed a spec ends with a **spec sync PR** in mm3-core (CORE-75): export both docs as Markdown to `docs/spec/core.md` and `contract.md`, run `tools/spec_sync.py` (regenerates `requirements.toml` and `versions.toml`; fails if a changed requirement is missing from a history row), assign new requirements to a milestone in `docs/spec/milestones.toml`, regenerate `docs/spec/coverage.md` with `tools/trace_report.py --out docs/spec/coverage.md`. A new requirement id prefix (such as PRS) must be known to `spec_sync.py` and `check_spec_refs.py` in the same PR. A row added to the 5.5 registry table also goes into `mm3.notifications.REGISTRY` in the same PR (`test_core_224_registry_matches_spec_table`); engine events are marked "event, engine only" there. When the export is too large to fetch in the chat, the same edits made in the master may be applied to the export by hand, and the PR says so (done for Core 0.46).
- `spec_sync.py` marks every requirement id named in a history row as changed in that version: in a history row, name only the ids added, changed or removed, never an id cited for context (a row that names CORE-281 or MOD-46 only to say what it extends makes them "changed" and every citation of them stale).
- To add behaviour next to requirements of a closed milestone without reopening it, write new requirements that state they extend the existing ones (as CORE-333..337 extend CORE-230..237 and CORE-346..348 extend CORE-277, CORE-22 and CORE-293) and leave the existing ones unchanged.
- A spec change proposed to the user and then declined before its spec sync PR is merged is reverted in the live spec documents (version, history row and text) and its PR is closed unmerged, so the masters, the exports on main and the log agree (done for ENH-011, 2026-11-13).

## Spec references in code (CORE-74, CORE-77)
- Every source file has an `Implements:` section in its module docstring; public classes and functions that implement specific requirements have one too. One entry per line:
  `<ids or ->: <spec name> <version>, §<section> <title>.`
  Example: `CORE-281: Core spec 0.45, §10.2 Packaging and deployment.`
- Use `-` instead of ids when the code implements a section without ids. Smaller fragments, workflows and TOML files use a comment: `# Implements CORE-184 (Core spec 0.5, §3.3 Scheduler): no overlap.`
- Test names cite requirement ids (`test_core_21_broadcast_excludes_sender`, `test_wth_08_stale_after_two_refreshes`); they count as test coverage. Cite a requirement only where the code actually implements it, not where it merely prepares for it.
- Staleness is per requirement: a citation stays valid until the cited requirement changes (`changed_in` in `docs/spec/requirements.toml`). A new spec version needs no code change by itself.
- `tools/check_spec_refs.py` fails CI on unknown or removed ids and non-existent versions. A stale citation fails only in files the pull request changes: a file you touch must be reviewed against the current spec and its citations updated.
- Coverage (CORE-78): `tools/trace_report.py` builds the matrix per milestone (implemented = cited by code, tested = cited by a test name). A milestone is done when its requirements are implemented and tested, or waived with a reason in `milestones.toml`; then set `status` and `done_at` there. Each requirement belongs to exactly one milestone; work it needs in a later milestone is noted there in a comment. A requirement counts as implemented as soon as code cites it, even when only a part of it is built (CORE-356 in 2026-11-14): when a PR builds a part, say so in the PR and in the log entry. A requirement implemented in another repository (the module-index builder for CORE-121 and MOD-96..99) is waived in `milestones.toml` with a pointer to the files and the PR there.
- When a closed milestone has requirements added or changed after `done_at`, the Traceability workflow keeps a `spec-change` issue open (CORE-79). Work it in a chat for that milestone; only the listed items are redone, not the whole milestone.
- Module repositories follow the same convention for the Module Contract.

## Repositories
- GitHub organization: mm3-project. License: MIT.
- mm3-project/mm3-core — engine, shell, admin UI, CLI, installer service, tooling (mm3.testing, mm3 module check, mm3 migrate), the `mm3-build` distribution, default modules (`modules/`, CORE-289) and the `mm3-modules-default` meta-distribution (CORE-294). Import package `mm3`.
- mm3-project/module-index — module catalog entries (modules/<name>.yaml), entry schema, validation and index build CI; its `publish.yml` workflow on main signs `index.json` (CORE-350); the name is fixed because the signing identity is `publish.yml@refs/heads/main`. The builder (`scripts/build_index.py` and its adapters, tested offline) lists only releases that pass `mm3 module check` on the wheel (CORE-121, MOD-96..99), whose SHA-256 matches PyPI and whose PEP 740 provenance names the entry's repository (CORE-123); a network failure aborts the build, so a partial index is never published; the `validate.yml` workflow runs the same build as a dry run on pull requests. GitHub Pages of this repository is set to the source "GitHub Actions". The first run of `publish.yml` (2026-11-14) published an empty index, because `modules/` had no entries yet.
- Third-party and non-default modules live in their own repositories (mm3-<name>).
- main is protected: pull request required, CI checks required. In development sessions, attach the relevant repository, work on its real files, commit to a branch and open a pull request.
- Never add commits to a pull request the user may already be merging; open a new pull request instead.
- Stacked pull requests (a code PR opened on top of its spec sync PR): after the lower PR is merged with squash, the **Restack** workflow in mm3-core (`tools/restack.py`, secret `RESTACK_TOKEN`) rebases the PRs stacked on it with `git rebase --onto origin/main <merged head>`, regenerating `docs/spec/coverage.md` on conflict. It comments on the PR when another conflict stops it; then rebase by hand (CONTRIBUTING.md, "Stacked pull requests"). Its push of a rebased branch is not a commit added to a PR being merged. The workflow fails when `RESTACK_TOKEN` has a lifetime of more than 366 days (an organisation policy; it failed on 2026-11-13 and 2026-11-14); then run `tools/restack.py` by hand (`--merged-sha <head of the merged PR> --merged-number N --prs <file with "<number> <branch>">`, then `--force-with-lease` against the old head), check that the final tree is unchanged, and wait for CI before asking the user to merge. A PR stacked on a stacked PR is rebased onto the new head of the PR below it (`--base`) and then onto main.
- Whenever you ask the user to merge a pull request, always state the merge method: **Squash and merge** (the default for every PR, one commit per PR on main), unless there is a stated reason for another method.
- Each repository has a CLAUDE.md pointing to these rules (`docs/rules.md` in mm3-core); keep it in sync when the rules change.

## Working method
- Before developing a feature, ask the questions needed to settle its requirements.
- Use only the approved stack (core spec 1.2). Propose any new library with rationale; adopt only after approval and add it to 1.2.
- Record decisions in core spec 1.1; never silently change a decided item.
- When a spec change affects these rules, update this file in the same turn and say so.
- When the user states an assumption about what the specs say or what the implementation does ("it is a gap", "the spec does not cover this"), verify it against the specs before building on it, and say plainly if it does not hold.
- Extending to other places (the user's standing instruction of 2026-11-14): when something that is added or changed in one place can also exist in other places (a style, a component, a dialog, a behaviour, a text, a check), ask the user whether to extend it to the others, and name the places. The proposed default is to extend it to all of them: the question is "extend to all?", not "extend at all?". Do not leave it in one place without saying so, and do not extend it without asking. When the user cannot be asked (an unattended run), extend it and say so in the result. A decision to extend a pattern to other pages or modules is a log entry when it is more than a few lines of work (see ENH-012).
- One chat per unit of work (a core milestone, one module, one tool, a dependency maintenance round); do not mix core and module development in the same chat.

## Dependency policy (core spec 10.9)
- Ranges in pyproject bounded to the current major; exact versions in uv.lock; commit both together. A pre-1.0 dependency (pypi-attestations) is bounded to its current minor.
- Each third-party library is used through one internal adapter in mm3.core (mm3.installer for the installer's libraries).
- Modules see only MM3-owned types plus Pydantic and FastAPI's APIRouter (MOD-94); ctx.http is an MM3 HttpClient.
- Renovate automerges tested patch/minor updates; Python versions in workflows are never bumped by Renovate.
- Deprecation warnings fail the tests. A vulnerability may be ignored in .pip-audit-ignore only with a reason, a date and a tracking issue.
- Prefer no dependency over an alpha or poorly maintained one when the needed part is small.
- Major updates are never merged automatically (full procedure in mm3-core CONTRIBUTING.md, "Major updates"):
  - `ci-tooling` (GitHub Actions, pre-commit hooks): read the release notes for breaking changes in our workflows, CI green, merge; no spec change.
  - `needs-spec-review` (runtime libraries in core spec 1.2): assess the migration guide and ask the user to adopt now, later or never (postpone = close the PR; reopen from the Dependency Dashboard). To adopt: update core spec 1.2 and bump its version, run a spec sync, fix the single adapter, update bounds and lock, CHANGELOG, CI green, merge.
  - `module-api` (Pydantic, FastAPI): implies a Module API major; keep the PR closed until one is planned.
- Dependency maintenance runs in its own chat (area: dependency maintenance), suggested monthly or when the Dependency Dashboard shows pending majors or the canary issue is open.

## Architecture invariants
- Modules use only MirrorModule, MirrorElement and ModuleContext; no engine internals.
- Modules read wall-clock time only through `ctx.now()`; the scheduler, budgets and `ctx.now()` share one engine clock, which `mm3.testing` replaces with virtual time (CORE-278, MOD-28).
- Every notification a module sends or handles, and every request it answers, is declared in `emits`, `consumes` or `answers` with Pydantic models (MOD-29); the README lists the names (MOD-24, MOD-41).
- All messages use the Notification envelope; CORE_* names are engine-only.
- Requests between modules use ctx.request / on_request (core spec 5.4); never send a request from on_request; handle RequestTimeoutError and RemoteError. Error replies carry code transient, configuration or internal (CORE-221); an on_request over budget sends no reply.
- Notification names in the shared registry (core spec 5.5) must carry the registered payload schema; incompatible changes use a new `_V2` name. Engine events consumed by modules (CORE_PAGE_CHANGED, CORE_CONFIG_CHANGED, CORE_CONFIG_ERROR, CORE_LOCALE_CHANGED, CORE_INTERACTION) are registered there too, and so are WEATHER_CURRENT (WTH-11) and PRESENCE_STATE (PRS-07). CORE_PRESENCE stays reserved and is never emitted (CORE-347).
- Pages (core spec 6.9): one current page for all displays; each instance is on all pages or on a list of pages, with an optional position per page. Hidden modules get suspend(); modules tolerate frequent hide/show (MOD-27). Runtime stop/start is never persisted. Hiding other modules requires the layout.control capability. A profile (MMM-ProfileSwitcher) is a page: pages may be out of the cycle (`cycle: false`), jump to a page after a time (`after`) and return to default when idle (`return_after`); PAGE_PAUSE / PAGE_RESUME and `/pages/pause|resume` set per-holder pause holds that stop only automatic changes; CORE_PAGE_CHANGED carries `previous` (CORE-333..337). The page indicator is a default module, not core.
- Never block the asyncio loop; blocking work goes through ctx.run_blocking.
- Front-ends never call any URL; data comes from their backend.
- `ctx.http` sends through the one engine transport (core 3.4, CORE-282..287): TLS always verified (a grant may name a CA file), no retries or cookies, loopback, link-local and multicast addresses refused unless the grant names the host, 60 s timeout cap. Modules never see httpx types and never log query strings, headers or bodies of requests.
- `engine.location` (lat, lon, name) is the shared place for modules, read as `ctx.location` / `this.location`; an instance may override it in its own config (CORE-288).
- Reference modules (core 9.4, CORE-289) live in mm3-core under `modules/`, each its own distribution: `mm3-greeting` (Contract §13 example, never published, not a default), `mm3-clock` (front-end only), `mm3-weather` (providers are plug-ins on `mm3_weather.providers`, Open-Meteo built in) `mm3-media` (full, MED-xx: video, image, slideshow, audio and YouTube through `ctx.media`) and `mm3-presence` (backend-only, core 9.2; display drivers are plug-ins on `mm3_presence.display`, `kiosk`, `ddcutil` and `cec` built in); clock, weather, media and presence are published and belong to `mm3-modules-default`. Their requirement ids are CLK-xx, WTH-xx, MED-xx and PRS-xx.
- Presence and power (core 9.2): presence is a module, not core. The engine only offers `ctx.system.request_suspend/request_resume` and `ctx.system.set_display_power(on)` (capability `system.power`), the last sent to the kiosk agent as `power {on}` and applied with `wlr-randr`; the power state is run-time, never saved, and reported in `CORE_DISPLAY_CHANGED` (CORE-346). Touches on the kiosk become `CORE_INTERACTION` (CORE-347). mm3-presence runs one instance with the states on → idle → off (idle only with a brightness driver), schedule windows and the presence sources MQTT topics, PRESENCE_DETECTED/CLEARED and touch; GPIO is not supported (PRS-01..08).
- The engine tells systemd its state with sd_notify (`READY=1` with CORE_READY, `STATUS=`, `RELOADING=1`, `STOPPING=1`; no-op without `$NOTIFY_SOCKET`) and pings `WATCHDOG=1` from a loop task that proves only event-loop liveness, never depending on modules, listeners or jobs (CORE-290, CORE-291). `mm3.service`, `mm3-kiosk.service` and `mm3-installer.service` ship inside the `mm3-core` package and are printed by `mm3 service unit`, `mm3 kiosk unit` and `mm3 installer unit` (CORE-292, CORE-143, CORE-357).

Only the installer verifies it: it keeps the verified index and the highest accepted `serial` in `/var/lib/mm3-install/catalog/`, refreshes daily and on `POST /v1/catalog/refresh`, re-verifies its own copy before every install and writes a copy to `/var/lib/mm3/catalog/` that the engine and the CLI read for search, info and list, which work from a stale cache (CORE-351). The installer downloads with the standard library only, from fixed hosts with size limits (CORE-370), and itself verifies the wheel's SHA-256 and its PEP 740 provenance against the index's publisher before building (CORE-352). Staged venvs are built with `python3 -m venv` and pip, constrained to the current venv's frozen versions; an operation that would change a package something else needs aborts (CORE-354). The installer protocol is HTTP/JSON on its socket with operations that outlive the engine's restart; `/v1/status` lists installed modules with their origin (CORE-355); the engine forwards them on `/api/v1/catalog*` and `/api/v1/installer*`, passing the passphrase through unlogged (CORE-356). The passphrase and TOTP are set only by a root peer (`sudo mm3 installer passphrase|totp`) and kept in `/var/lib/mm3-install/auth.json` (CORE-369). After a restart READY is the unit active within 60 s, then `mm3 diag check`; a polkit rule lets `mm3-install` stop, start and restart `mm3.service`, restart `mm3-kiosk.service` and reboot the system through logind, and nothing else (CORE-357, CORE-359, CORE-382). A removal first saves a config version disabling the module's instances (CORE-358). The index is built by the `publish.yml` workflow of module-index (core 10.6, CORE-121, CORE-123, CORE-350): a release is listed only if its wheel's SHA-256 equals PyPI's, its PEP 740 provenance names the entry's repository and `mm3 module check` on the wheel is compliant; the workflow named in the attestation may differ between releases of the same repository (each wheel is verified for the publisher its own attestation claims, and the entry's `publisher` in the index is the newest listed release's, so an older release from another workflow can be listed yet fail verification when installed; a `publisher` per release would be a spec change, decided on 2026-11-14 not to be done now); the build signs keyless on main only and aborts on any network failure.
- Backup and restore (core 10.8): the installer schedules backups itself at `backup.schedule`, reading the running `backup` block over the admin socket, and catches up a missed run older than 24 h (CORE-360); the engine forwards `/api/v1/backups*` (uploads ≤ 2 GiB), and only restores need re-authentication (CORE-361). An archive is a `.tar.gz` (`manifest.json`, `config/`, `data/<instance>/`, `modules.json`, `secrets/`), age-encrypted whole when encrypted, named `<hostname>-<stamp>-<kind>.mm3backup` with an unencrypted sidecar `.mm3backup.json` that holds no secrets; another hostname is a warning (CORE-362). A restore stops `mm3.service`, writes secrets, data and config files, rebuilds the venv for `modules`, and starts the engine, which records a history version with reason `restore` (CORE-363). The age identity is shown once and kept only on request (`/var/lib/mm3-install/backup.key`); a key sent with a restore lives only in the installer's private tmp (CORE-364). rclone remotes live in the installer's own `rclone.conf`, secrets shown as `!masked`; a remote failure never fails the local backup (CORE-365). Pre-operation backups (kind `pre`, last 3, outside `keep`) precede every restore, module change and engine upgrade, and their failure stops the operation (CORE-366). Backups containing secrets are always encrypted; `backup.parts` with `secrets` requires `encrypt_to` (CORE-161, CORE-244).
- An invalid configuration never replaces the running one. Configuration history is append-only and stores the whole config set (main file, includes, widget templates, custom.css; never the env file); undo, redo and restore always create a new validated version.

## Code standards
- Full type hints, mypy --strict and ruff clean.
- Google-style docstrings on every public class and function, with the `Implements:` section above.
- Every config is a Pydantic model; file and GUI edits use the same validator.
- Logging only via ctx.log / this.log, as structured events.
- Tests named after requirement ids; >= 85 % coverage on mm3.core.
- Every module passes `mm3 module check` before it is delivered (CORE-281; exit 0 compliant, 1 MUST failed, 2 tool error), and its warnings are read too: a config field without a translated label (MOD-46) is only a warning (CORE-310), so a module delivered here has none. Catalog modules also meet MOD-96 to MOD-99. Suppression pragmas (`# mm3: allow MOD-xx <reason>`) silence SHOULD findings only, never a MUST. A module whose configuration cannot be sampled sets `[tool.mm3.check] config` / `grants` in `pyproject.toml` (Contract §12.1).

## Internationalisation
- No literal user-facing strings; UPPER_SNAKE catalog keys via t().
- Ship EN, IT, FR, ES, DE for every user-facing module; a new language needs no code change.
- Catalogs are compiled when the package is built and shipped in the wheel (`.mo` + `messages.json`) by the `mm3-build` hook `mm3-i18n`, the only compiler (CORE-280); the engine never compiles at run time and reads `messages.json` for backends and browsers (CORE-263). `mm3 i18n compile` builds them; `mm3 i18n check` (in CI) fails on missing or out-of-date compiled files, missing keys or different placeholders.
- Lookup: module catalog along the locale chain, then the core catalog; locale packages (`mm3.locales`, named after the module or `mm3`) rank below the module's own entries (CORE-264).
- User-typed text uses LocalizedText.
- User-facing modules provide a HEADER catalog key (MOD-67).
- Config form labels and help are each field's schema `title` and `description`, which are catalog keys (MOD-46, `CFG_<NAME>` / `CFG_<NAME>_HELP`) in the catalog of the module that owns the model; the engine's own fields use `CFG_<SECTION>_<FIELD>` in the core catalog; nested models and list items use their own model's keys. A missing label shows the field name. `mm3 module check` reports missing keys as a SHOULD (a warning); mm3-core CI fails on them for the engine and the reference modules (CORE-310). It stays a warning for every other module: the user decided on 2026-11-13 not to add a strict mode (ENH-011, rejected), so a new module gets its labels only if its author reads the warnings. The admin UI follows `engine.locale` unless the admin picks a shipped language for the session with `PUT /api/v1/session/locale` `{locale}` (null to follow the engine again; admin session only), never `Accept-Language` (CORE-309). The `header` of `GET /api/v1/installed-modules` is the module's `HEADER` entry in that admin language, or the module name when it has none (CORE-380). The labels of the MQTT indicator and of the admin home status view are core catalog keys in the admin language (CORE-381); so are the labels, dialog texts and banners of the System card (CORE-383), the texts of the shared dialogs, banners and action rows of every admin page (CORE-384..387) and the texts of the Catalog page (`CORE_ADMIN_CATALOG_*`, CORE-120) and of the Backups page (CORE-361).
- Home Assistant entity names are catalog keys resolved in `engine.locale` (core `HA_*` keys for the engine's entities, the module's own keys for `ha_entity()`), republished on `CORE_LOCALE_CHANGED` (CORE-343, CORE-344).
