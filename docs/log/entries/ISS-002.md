# ISS-002 — Changed module parameters not applied until disable/enable
- Reported: 2026-11-07
- Type: issue
- Priority: P3 (set by the user: there is a workaround)
- Area: core (hot reload), shell (front-end), modules, configuration
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: "modifying parameters on modules is not applied immediately but requires a disable/enable" (as reported). Not stated: whether the parameters were changed in the admin UI (Layout, Form or YAML tab) or in the config file, and which module. On 2026-11-17 (Core 0.45, Contract 1.0 rev 15), after further testing: "none of the specific module settings are updating the instance, neither immediately nor at save after save" (as reported): every module-specific setting, in the preview and on the mirror, after each save.
- Workaround: disable and then enable the module (instance) (as stated by the user)
- Expected / proposed: a changed parameter takes effect without a disable/enable. The backend already does this (CORE-210); the front-end element has to receive the new public config too. Options for the fix, proposed by Claude on 2026-11-17, to be chosen by the user: (A, recommended) the shell treats a changed public config like a changed module: it removes the element and creates it again with the new config, as a disable/enable does today; CORE-275 changes ("keeping elements whose instance, module, version and public config are unchanged"), no Module Contract change; (B) a new front-end callback `onConfigChange(config)` in Contract §5.1, whose default re-creates the element, so a module can apply cheap changes live as MOD-50 allows for backends; Contract revision 16 and CORE-275 change.
- Requirements: Core 0.46: CORE-275 changed (option A). Before: CORE-275 (on `reload` `resync` the shell keeps elements whose instance, module and version are unchanged; nothing gives a kept element the new public config) and Module Contract §5.1 and §5.2 (`this.config` is set once; no callback for a config change): spec gap, found on 2026-11-17. CORE-210, CORE-195 and MOD-50 are met by the backend (checked 2026-11-14 and 2026-11-17).
- Spec check: 2026-11-07, Core spec 0.38 and Module Contract 1.0 rev 15. Searched "hot reload", "CORE_CONFIG_CHANGED", "reconfigure" and "CORE-195"; read the table "On hot reload (6.3)" for the top-level keys (engine settings, not module parameters). Not checked: the implementation plan, section 6.3 in full, the actual code. Found:
  - CORE-210: once validation passes, the new version is recorded and applied in this order: stop removed and replaced instances; call `reconfigure()` on instances whose config changed, restarting those that return False; start added instances; push layout and display changes to browsers; then emit `CORE_CONFIG_CHANGED`. A DISABLED instance whose config changed is restarted (CORE-195).
  - Contract: `reconfigure(new)` is a lifecycle call under the engine budget (an overrun counts as an exception). MOD-50: `reconfigure()` should apply changes live where cheap, and returning False is always correct (the engine then restarts the instance).
  - CORE-275: a hot reload that changes an instance's public config sends `reload` `resync` to the shells.
  Result: the user's assumption (a spec gap) is not confirmed. The spec requires a changed module parameter to be applied by `reconfigure()` or by a restart, with no disable/enable. Behaviour that needs a disable/enable therefore deviates from CORE-210 in the core, or, if the module's `reconfigure()` returns True without applying the change, from MOD-50 in the module. Not found in what was read: how the user is told whether a change applied live or by restart (a possible, minor, spec point).
  Second check, 2026-11-17, Core spec 0.45 and Module Contract 1.0 rev 15 (the exports `docs/spec/core.md` and `contract.md` on main 47e50fc) and the code on the same commit. Searched in the specs "onConfigChange", "this.config", "resync", "recreate" and "rebuild from"; read CORE-275 and Contract §5.1 and §5.2. Found: CORE-275 says that with `resync` the shell "rebuilds from the new `welcome`, keeping elements whose instance, module and version are unchanged", and that a change of public config sends `resync`; Contract §5.1 lists the element callbacks (`render`, `onMessage`, `onNotification`, `onResize`, `onSuspend`/`onResume`, `onLocaleChange`, `onPageChange`) and none for a config change; §5.2 gives `this.config` as the public config. In the code: `plan_reload` puts the instance in `plan.reconfigure`, `Instance.reconfigure` restarts it (the default `reconfigure()` returns False), and `ShellHub.reloaded` (`web/ws.py`) sends `reload` `resync`; the shell (`web/static/shell.js`, `onWelcome`) keeps a cell whose key `module|element|scripts` is unchanged and calls `updateCell`, which sets only the appearance and the header; `this.config` of the element is set only when the element is created (`mm3.js`, bind). So the backend applies the change, but the element on the mirror and in the preview keeps its old config until it is removed and created again, which is what a disable and an enable do. A front-end-only module (mm3-clock) therefore never shows a change; a module with a backend shows the change only where its rendering depends on the backend's state. Result: the 2026-11-07 conclusion (no spec gap) is corrected: the cause is a spec gap in CORE-275 and Contract §5 (what a kept element receives when its public config changes), which the shell implements literally. Not reproduced on the user's mirror; not checked: third-party modules.
