# ENH-005 — Sleeker, more modern look for the admin pages, same functionality; the current UI stays as an alternative
- Reported: 2026-11-12
- Type: enhancement (the user asked "would it be difficult to have a nicer ui for the admin pages?", then approved a mockup and asked to set it as a new requirement)
- Priority: P3 (set by the user: "low pri, non blocking"; on the enhancement scale "maybe in the future")
- Area: admin UI, front-end, look and feel (all admin pages)
- Spec versions at report: Core spec 0.38, Module Contract 1.0 rev 15
- Description: the user finds the admin pages "really scant graphically" and wants "something more sleek and modern", with the same functionality unchanged. Direction approved by the user on 2026-11-12: the mockup of `/admin/config` (Layout tab) made in this chat as a Design artifact, "MM3 admin config refresh" (https://claude.ai/artifact/JNk1UxfG5y3EvRYk7aJBaq): dark theme, sidebar navigation, page header with the draft state, Save/Discard and undo/redo buttons, tabs Layout/Form/YAML/History, page selector, mirror preview, inspector panel for the selected instance, switchable accent colour. The mockup is a direction, not a final design; its own look (no design system exists yet).
- Workaround: the current UI (it works; it is only plain). The user states the current UI is also the alternative: it is to be kept, selectable, after the new look is added.
- Expected / proposed: a new look for all admin pages with identical functionality, delivered as an option next to the current look, which stays available. Points to settle when it is defined: how the user chooses between the two looks (an admin setting, a per-browser choice, a URL parameter) and which is the default; the scope of the current look (kept unchanged, or only maintained); the pages in scope (config with its four tabs, status, modules, catalog, widgets, backups, debug, login, extension pages `/admin/ext/<module>`); the design tokens and where they live (separate from the mirror theme variables of CORE-261 and from the Module API, MOD-33); light theme or dark only, and responsive behaviour on a phone or tablet; accessibility (contrast, focus, keyboard); icons and font under the vendored-assets rules (CORE-323 and the fonts rule); language of the admin (CORE-309) unchanged; the effect on the in-house components (`<mm3-schema-form>`, layout overlay CORE-326) and on test and CI cost (screenshots, accessibility checks); whether the design is described in the spec (principles and tokens) or only in the implementation.
- Requirements: none: spec gap. Related, likely to be extended or changed: CORE-322 (the admin config page and its tabs), CORE-63 (CSP: no inline script or style on shell and admin pages, which the real implementation must respect even though the mockup uses inline styles), CORE-261 (theme variables, mirror), CORE-309 (admin language), CORE-323 (vendored front-end assets), CORE-326 (layout overlay).
- Spec check: 2026-11-12, Core spec 0.38 and Module Contract 1.0 rev 15 as already searched in this chat (the terms "dark" and "responsive" gave no hits; the admin front-end stack is the no-build vanilla Web Components set of requirements cited above). Not re-searched on this date: the implementation plan, the code, the spec text on fonts and icons in full. Found: no requirement on the visual design, theme or layout of the admin pages; the spec fixes the stack, the tabs of `/admin/config`, the CSP and the vendored assets, not the look. Result: confirmed as a spec gap. The CSP and no-build constraints do not prevent a restyle (external stylesheets and CSS variables are allowed), so the change is feasible within the current stack; the cost is mostly design and testing, not architecture (see the answer given in the chat on 2026-11-12).
- Status: open — to go through the defining phase before any code, when the user decides to act on it
