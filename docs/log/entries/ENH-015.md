# ENH-015 — Compliance checklist rows (Contract §11) and checks for the media requirements MOD-100..103
- Reported: 2026-11-20 (milestone 8, step 7, PR #160 `ctx.media`; the user asked to postpone the §11 rows and to write in detail how to handle them in a dedicated chat: "Si rimandiamolo. Ma scrivi pure nel dettaglio come gestirne l'adempimento in apposita chat")
- Type: enhancement (the requirements MOD-100..103 exist and the code behind them is built, but the checklist that `mm3 module check` reports has no row for them)
- Priority: P2 (proposed by Claude: the Contract's own history row for rev 16 promised the rows "in the development of milestone 8", so the milestone should either do this before its close or carry it over in `milestones.toml`)
- Area: tooling (`mm3 module check`, `src/mm3/core/modcheck/`), specs (Module Contract §11 and Document history)
- Spec versions at report: Core spec 0.57, Module Contract 1.0 rev 16
- Description: Contract rev 16 (19 Nov 2026) added MOD-100..103 (ctx.media, takeover, front-end media rules, youtube grant and test kit fakes) but not their rows in §11. `mm3 module check` reports only what `catalog.py` lists, so a module that builds a media URL by hand, or does not stop its players in `onSuspend`, passes the check today. The only media check that exists is the one from step 4: `static.py` (`MEDIA_ELEMENTS`) makes a front-end that uses `mm3-player` or `mm3-youtube` declare `media.play` or `media.youtube`; it is reported under MOD-70, not under a media row.
- Workaround: none needed for the engine. Until the rows exist, the reference module `mm3-media` and any other media module are checked by their own tests (`h.media`, `BrowserHarness(media=)`) and by review.
- Expected / proposed: see "Plan for the dedicated chat" below. Summary: add §11 rows for MOD-100, MOD-101, MOD-102 and MOD-103, implement their checks in `modcheck`, publish Contract rev 17 with a Document history row, and run the spec sync PR.
- Requirements: MOD-100, MOD-101, MOD-102, MOD-103 (no row). Related: MOD-27 (suspend and resume), MOD-70 and MOD-71 (capabilities), MOD-72 (degrades without grants), MOD-97 (README lists grants), CORE-281 (`mm3 module check`), CORE-409 and CORE-413 (`mm3-player`, `mm3-youtube`).
- Spec check: 2026-11-20, Core spec 0.57 and Module Contract 1.0 rev 16, searched in `docs/spec/contract.md` (§4.5, §11, §12.1, Document history), `docs/spec/milestones.toml` (milestone 8 comment), `src/mm3/core/modcheck/catalog.py` and `src/mm3/core/modcheck/static.py`. Found: MOD-100..103 in §4.5; no row for them in §11; the rev 16 history row saying their rows "come with the checks in the development of milestone 8"; the `catalog.py` docstring listing engine-side and catalog rows that are not reported; the step 4 comment in `milestones.toml` ("MOD-103 only in part: the check rows of the media elements"); the `MEDIA_ELEMENTS` capability check in `static.py`. Not searched: `docs/rules.md` on how a §11 change is classified (defining phase or development), the implementation plan (a Claude Doc that could not be read as text in the chat of 2026-11-20), the module-index repository (the catalog rows MOD-96..99 live there). Result: confirmed as far as searched: a spec gap, to be closed in a defining phase before the check code.

2. Defining phase: settle with the user the four rows. Proposal to start from (levels and categories are Claude's proposal, to be confirmed; categories as in §11: static, kit, harness, review):
   - MOD-100 (ctx.media: grant, `sources()`, `url()` and `files()`): MUST, kit. The kit runs the module against `h.media` with a grant that lacks a source and expects `PermissionError`, and an unknown source or file and expects `ValueError`, handled without a crash (this overlaps MOD-72, so the report text must say what is new). Static is not needed: the capability is already checked by MOD-70.
   - MOD-101 (takeover and stop): MUST, kit. Takeovers and stops are recorded by `h.media`; the check confirms the module stops only what it started (`stop()` without an id never touches another owner's takeover) and does not call `takeover()` from a hook that runs on every refresh without a reason (ask whether that second part is a SHOULD review row instead).
   - MOD-102 (front-end media rules): MUST for the first sentence, static (JS scan with `jsscan.py`): no `<video>`, `<audio>`, `<img>` or `new Audio` pointing at a media URL, no string literal that starts with `/media/`, no iframe to YouTube; media only through `mm3-player` and `mm3-youtube`. MUST, harness for the second sentence: a `BrowserHarness` run where the fixture source fails and the module shows a localized message on `mm3-media-error` (five languages, as MOD-72 and MOD-65 do), and `onSuspend` stops the players (no player left playing after `suspend`). Decide whether the static part is a warning or an error (false positives: a module that serves its own non-media `/media/` path is unlikely, but the scan must be tested on a counter-example).
   - MOD-103 (youtube grant and the kit's fakes): decide between (a) a row, MUST, static: a front-end that uses `mm3-youtube` declares `media.youtube` (this is already reported under MOD-70, so the row would move that finding to MOD-103) and the README names the `youtube` grant (MOD-97); or (b) no row of its own, with the rev 17 history row stating that MOD-103 is covered by MOD-70 and MOD-97 and that its test kit half is not something a module can fail. Recommended: (b) unless the user wants the finding to carry the media id. State the choice in the history row either way.
